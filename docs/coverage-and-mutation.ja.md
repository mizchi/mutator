# コードカバレッジとミュータントテスト

[English](coverage-and-mutation.md)

コードカバレッジとミュータントテストは、同じものを違う強さで測っているわけではありません。欠陥がテストに捕まるまでの経路のうち、別々の段階を測っています。2 つの数字を平均すると、分母の違うものを混ぜることになり、意味がなくなります。1 本の漏斗の各段階として読むのが正しい扱い方です。

## 欠陥が検出されるまでの経路（RIPR）

テストが欠陥を検出できるのは、次の 4 つがすべて起きたときだけです。

| 段階 | 問い | 測るもの |
|---|---|---|
| **R**each（到達） | 欠陥のあるコードをテストが実行するか | コードカバレッジ / NoCoverage |
| **I**nfect（感染） | 実行したとき、値や状態が実際に変わるか | weak mutation（dry run が記録する） |
| **P**ropagate（伝播） | その変化がテストから観測できる所まで届くか | ミュータントテスト |
| **R**eveal（顕在化） | assertion がそれを検査しているか | ミュータントテスト（Killed / Survived） |

コードカバレッジが見ているのは最初の段階だけです。どれかのテストがその行を実行すれば、assertion があってもなくても「カバー済み」になります。ミュータントテストは 4 段階すべてを通した最終結果を、Killed か Survived かの 1 ビットで返します。だからカバレッジ 100% でも、何も検出しないことがあります。実例として、[defu の「plain object だけマージする」修正](benchmark.md#survivor-usefulness-on-the-five-small-projects-2026-10-12)は、テストを 2 本追加しましたが、両方とも `it.skip` のままでした。有効にしても `toEqual` で比べているので、クラスのインスタンスと plain object を区別できません。

## スコアは混ぜずに分解する

行ではなく mutant の数で数えると、ミュータントスコアは 2 つの量の積に分解できます。

```
ミュータントスコア = 到達率 × テストの強さ
                  = (いずれかのテストが実行する mutant / 全 mutant) × (Killed / いずれかのテストが実行する mutant)
```

- **到達率：** 壊し方の数で重み付けしたコードカバレッジです。mutant が 5 つある行は 5 回数えられます。
- **テストの強さ：** カバレッジからは見えない量です。テストが実行するコードのうち、欠陥を実際に捕まえられる割合を表します。StrykerJS は "mutation score based on covered code" として出しています。

この 2 つは分けて報告してください。到達率が低ければテストケースが足りていません。テストの強さが低ければ、入力か assertion が弱いということです。1 つに混ぜた数字では、どちらの問題なのかが見えなくなります。

## 穴は 3 種類、直し方も 3 通り

mutator は検出されなかった mutant ごとに、テストがどの段階で止まったかを報告します。

| 穴 | テストは… | 直し方 | 実例 |
|---|---|---|---|
| **not detected**（検出されない） | 実行するが、どれも失敗しない | assertion を強くする（または等価 mutant として受け入れる） | defu は同一性が要る所で `toEqual` を使っている。ufo は `withBase` を、ベースの直後が `?` の場合で一度も検証していない |
| **not infected**（感染しない） | 実行するが、値が変わる入力を一度も与えない | 入力を足す（境界値、別のケース） | pathe のドライブレター判定は `a:` / `z:` で試されていない。どのテストも触れない `>=` → `>` の境界 |
| **not reached**（到達しない） | 一度も実行しない | テストケースを足す | scule の `{ normalize: true }` 分岐。uneffect のパースエラー時の早期 return |

この 3 区分は次の形で出力されます。
- **テキストの要約：** 3 つを別々の見出しで列挙します。
- **GitHub の注釈：** タイトルが "Mutant not detected"、"Mutant not infected"、"Mutant not reached" になります。
- **JSON レポート：** 標準のステータス（`Survived` / `NoCoverage`）はそのまま使い、not infected の mutant には `statusReason` を付けます。
- **not reached の注釈：** `--since` を付けたときだけ出します。プロジェクト全体で出すと、他の指摘が埋もれてしまうためです。

感染するかどうかが分かるのは、副作用のない式に限られます。具体的には、識別子・リテラル・`.length` の比較や算術と、`true` / `false` に置き換えた条件です（README の [Weak mutation](../README.md#weak-mutation) を参照）。それ以外の mutant は、どのテストからも感染していなくても、生き残れば not detected として報告されます。たとえば、効果にどのテストも届かない文の削除もここに入ります。つまり、not infected は確実な判定で、not detected はどれにも当たらなかった場合の既定値です。

どの入力でも差を観測できない mutant もあります。これを等価 mutant と呼びます。null にならない値への `?.`、順序を誰も見ない `.sort()`、性能改善で入れた高速経路を無効にする変更などです。等価 mutant は not detected として表示されます。そのため、ミュータントスコア 100% は一般には到達できません。目標値にはしないでください。

型だけで等価だと分かるものもあります。プロジェクトで `strictNullChecks`（または `strict`）と `noUncheckedIndexedAccess` が有効なら、型チェックの段階で `a?.b` → `a.b` のうち `a` の型が `null` も `undefined` も含まないものを除外し、not detected ではなく `Ignored`（`equivalent: a is never nullish`）として報告します。件数はサマリに `equivalent by types: N` と出ます。これは型を信用した判定です。キャストや `any` で nullish な値が隠れていれば、判定は誤ります。それ以外の等価 mutant は人が判断する必要があり、その判断は `mutator accept` で記録できます。

## 使い分け

1. **コードカバレッジは、プロジェクト全体の地図として使います。** 安く測れて、テストがまったく無い場所が分かります。ただし目標値にすると、assertion なしでコードを実行するだけで簡単に上げられてしまいます。
2. **ミュータントテストは、変更に対する検査として使います。**
   - PR で `--since` 付きで回し、3 つの区分をレビューの指摘として読みます。
   - 過去コミットで試した結果、変更行の Survived が本当のテストの穴だった割合は、小さいライブラリ 5 つで 77% でした。レポート用の文字列や冗長なガードが多い大きな解析器では 36% でした（[benchmark](benchmark.md#are-the-survivors-worth-acting-on-10-past-commits-2026-10-11)）。
   - プロジェクト全体で回すと、以前からある Survived が新しい分より多くなり、実行コストもずっと大きくなります。
3. **スコアは作業リストとして扱い、KPI にはしないでください。** 等価 mutant があるので 100% には届きません。最後の数ポイントを追うと、実装の細部を assert するだけのテストが増えます。
4. **変更行の not reached は、粒度の細かいカバレッジとして読みます。** コードカバレッジと重なる部分はありますが、diff の中では「どのテストも通らない分岐や部分式」をピンポイントで指します。たとえば条件式の `: []` 側のフォールバックです。

## 実際に踏んだ落とし穴

- **runner が集めるテストの集合も、結果の一部です。** runner が集めないテストファイルは、何も kill できません。例としては、統合テストを外した CI の tier や、そのファイルにマッチしない `include` の glob があります。ある計測では、Survived 32 件のうち 18 件が、実はそのコミット自身のテストで落ちる mutant でした。選んだ tier がそのテストを外していたためです。今は `--since` のとき、変更されたテストファイルを runner が集めていなければ警告を出します。
- **子プロセスでソースを実行するテストは、mutator がメモリ上で適用した mutant を見ません。** そうしたテストでしか通らないコードの mutant は、not reached や Survived に見えてしまいます。今は dry run の間に、各テストが `node:child_process` で起動したプロセスを記録しています。コマンドラインにプロジェクト内のファイルが含まれていれば、そのテストを警告として一度だけ表示します。さらに、そのエントリーファイルが import しているファイルの未検出 mutant には「possibly reached in a child process（子プロセスで実行されている可能性あり）」というラベルを付けます。こうした mutant も一覧には残りますが、別のグループにまとめられ、`--fail-on-survived` の対象からは外れます。エントリーからたどるのは静的な import だけです。ビルド成果物（`dist/`）やパッケージの bin を起動するコマンドは、プロジェクト内のファイルを名指ししていれば一覧には載りますが、元のソースまではたどりません。
- **commit が触れた行だからといって、commit が変えたコードとは限りません。** 古いガードの mutant でも、commit が同じ行を編集したせいで PR に出てくることがあります。
